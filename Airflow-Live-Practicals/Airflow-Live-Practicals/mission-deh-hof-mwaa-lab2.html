Diamond — Trigger One DAG from Another with Assets

Sachin Chandrashekhar — Data Engineering Hub

✅ Prerequisite — finish Lab 1 first. This lab reuses the same MWAA environment, Glue jobs, and S3 buckets you created in Lab 1. If you already tore everything down, re-run the one-shot setup before starting. Region must be us-east-1.
💎 Lab Objective: So far one DAG ran all three Glue jobs in a line. In the real world, different teams own different stages, so pipelines are split across DAGs that hand off through data, not a fixed schedule. You'll build two DAGs: a producer that creates curated data, and a consumer that is automatically triggered the moment that data is produced — using Airflow 3's Asset (data-aware) scheduling.

⏱️ Estimated time: ~20 minutes

Part 1 — The Concept: Data-Aware Scheduling

In Lab 1 your DAG ran on a time schedule (@monthly). But what if the right trigger isn't "it's 6 AM" — it's "the upstream data just landed"? That's data-aware scheduling.

🧠 What is an Asset? An Asset is just a named piece of data (identified by a URI, like an S3 path). A producer task declares it updates that asset. A consumer DAG says "run me whenever that asset updates." Airflow wires the dependency for you — no schedule, no sensor, no polling.
ℹ️ Key rule: Airflow marks an asset as updated only if the producer task succeeds. If it fails or is skipped, the consumer DAG does not run. The hand-off is safe by design.

🏗️ What We're Building

⏩ Short on time, or just want it to work? Ready-made copies of both DAGs are in the backup-dags/ folder of the Live Session bundle — nyc_tlc_producer.py and nyc_tlc_consumer.py. Part 2 — Build DAG 1: The Producer

Estimated time: 8 minutes

In Kiro, create a new file nyc_tlc_producer.py. It runs the ingestion Glue job and declares the raw Asset as its output — representing "fresh raw data has landed."

Step 1 — Imports

Note the Asset import comes from airflow.sdk (the Airflow 3 way).

from datetime import datetime from airflow.sdk import DAG, Asset from airflow.providers.amazon.aws.operators.glue import GlueJobOperator

Step 2 — Define the shared Asset

This is the "contract" between the two DAGs. The URI is just a logical label — it does not have to be a real, resolvable S3 path; Airflow only uses it to match producer and consumer. We name it after the raw data so it's meaningful. Both DAGs must use the exact same URI string.

raw_asset = Asset("s3://mission-deh-hof/nyctlc/fhvhv_tripdata_raw")
ℹ️ Because this is just a label, there's no account ID to insert — leave the string exactly as shown so it matches in both files.

Step 3 — Define the producer DAG and its task

The ingestion task adds one new argument: outlets=[raw_asset]. That's the only line that makes this a producer.

default_args = { 'owner': 'mission-deh-hof', 'retries': 1, } with DAG( dag_id='nyc_tlc_producer', default_args=default_args, schedule='@monthly', start_date=datetime(2026, 1, 1), ) as dag: data_ingestion = GlueJobOperator( task_id='data_ingestion', job_name='mission-deh-hof-nyctlc-ingestion', outlets=[raw_asset], # 👈 declares this task PRODUCES the raw asset )
ℹ️ outlets is the whole trick. When data_ingestion succeeds, Airflow records an "asset update" event for raw_asset. That event is what wakes up DAG 2.

Part 3 — Build DAG 2: The Consumer

Estimated time: 5 minutes

Create a second file nyc_tlc_consumer.py. It runs raw_to_curated then curated_to_aggregated. The magic is in the schedule — instead of a cron string, it's a list containing the Asset.

Step 1 — Imports (same Asset import)

from datetime import datetime from airflow.sdk import DAG, Asset from airflow.providers.amazon.aws.operators.glue import GlueJobOperator

Step 2 — Re-declare the SAME Asset

Use the identical URI string from DAG 1. This is how Airflow knows the two DAGs are talking about the same data.

raw_asset = Asset("s3://mission-deh-hof/nyctlc/fhvhv_tripdata_raw")

Step 3 — Schedule the DAG ON the Asset, then define its tasks

default_args = { 'owner': 'mission-deh-hof', 'retries': 1, } with DAG( dag_id='nyc_tlc_consumer', default_args=default_args, schedule=[raw_asset], # 👈 run whenever raw_asset is updated — no cron! start_date=datetime(2026, 1, 1), ) as dag: raw_to_curated = GlueJobOperator( task_id='raw_to_curated', job_name='mission-deh-hof-raw-to-curated-etl', ) curated_to_aggregated = GlueJobOperator( task_id='curated_to_aggregated', job_name='mission-deh-hof-curated-to-aggregated-etl', ) raw_to_curated >> curated_to_aggregated
⚠️ The URI in both files must match character for character. A trailing slash or a typo means Airflow treats them as two different assets, and the consumer will never trigger.

Part 4 — Upload Both DAGs & Watch the Hand-Off

Estimated time: 7 minutes

Steps

  1. Upload both files — nyc_tlc_producer.py and nyc_tlc_consumer.py — to the dags/ folder of the DAGs bucket (S3 Console → bucket → dags/ → Upload, same as Lab 1)
  2. In the Airflow UI, wait ~1–2 min for both DAGs to appear, then unpause both (nyc_tlc_producer and nyc_tlc_consumer)
  3. Open nyc_tlc_consumer — notice its schedule shows the Asset, not a cron. It just sits idle, waiting. Do not trigger it manually.
  4. Trigger nyc_tlc_producer manually (▶). Watch it run data_ingestion.
  5. The moment data_ingestion turns 🟢 green, watch nyc_tlc_consumer — within a few seconds Airflow auto-starts a run of it (raw_to_curated → curated_to_aggregated), with no manual trigger. 🎉
ℹ️ See the relationship visually: in the Airflow UI go to Assets (top menu). You'll see the raw asset with nyc_tlc_producer as its producer and nyc_tlc_consumer as its consumer — the dependency graph Airflow built from your two Asset declarations.
✅ You just built a data-driven pipeline across two DAGs. DAG 2 ran because the data it needed was produced — not because a clock said so. This is how modern, decoupled pipelines hand off between teams.

Part 5 — Tear It All Down (Do Not Skip)

Estimated time: 15–20 minutes

MWAA bills continuously while it exists. When you finish, run the one-shot teardown. It removes everything the setup created — MWAA first (to stop the hourly billing fastest), then the full pipeline.

Run this

cd ~/scripts && chmod +x mission-deh-hof-teardown-all.sh && ./mission-deh-hof-teardown-all.sh

What happens, in order

PhaseWhat it removes
Step 1 — MWAAEmpties the DAGs bucket (all object versions + delete markers), deletes the CloudFormation stack (MWAA env, VPC, NAT gateways, IAM role), polls until DELETED.
Step 2 — PipelineDeletes Glue jobs/crawlers/databases, Step Functions, EventBridge schedule, SNS topic, DynamoDB tables, the data-lake S3 bucket, and the Glue IAM role.

Wait for the final "ALL DONE — billing has stopped" message.

⚠️ This permanently deletes both S3 buckets and all their contents, the MWAA environment, VPC and networking, DynamoDB tables, and all IAM roles. Download anything you want to keep first.
ℹ️ If the MWAA stack shows DELETE_FAILED, the script prints the failing resources and continues to the pipeline teardown anyway. Re-run the command, or delete the flagged resource in the console, then re-run.
✅ When the stack is gone, billing stops. Confirm in CloudFormation → Stacks that mission-deh-hof-stack no longer appears.
