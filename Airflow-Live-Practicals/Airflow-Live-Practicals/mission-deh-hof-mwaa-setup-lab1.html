The mw1.micro environment used here bills per hour the environment exists (plus NAT Gateway, Elastic IPs, and S3) — roughly $0.49/hour (~$12/day) as a rough guide, varying by region and usage. Tear the environment down the moment you are done using the teardown script in this lab. Leaving it running overnight is the single most common way learners get a surprise bill.

Part 2 — Run the Full Setup (One Command)

Estimated time: ~45–55 minutes (mostly unattended)

This single command unzips the bundle, enters the scripts/ folder, and runs the one-shot setup. It provisions the pipeline first, then deploys MWAA.

Run this

unzip -o scripts.zip && cd scripts && chmod +x mission-deh-hof-setup-all.sh && ./mission-deh-hof-setup-all.sh
ℹ️ Replace scripts.zip with your actual zip filename. If your zip extracts the files directly instead of into a scripts/ folder, drop the cd scripts && part.

What happens, in order

PhaseWhat it doesTime
Step 1 — PipelineCreates the S3 data lake, 3 Glue jobs, databases, crawlers, DynamoDB tables, SNS topic, and Step Functions state machines. Runs the ingestion job.~5–10 min
Step 2 — MWAACreates the CloudFormation stack (VPC, DAGs bucket, Airflow 3.0.6 env), waits for CREATE_COMPLETE, prints stack outputs, and creates the dags/ folder.~20–40 min
  1. During Step 1 the script will pause and ask for your email for pipeline alerts. Type your email and press Enter. Then check your inbox and confirm the SNS subscription (check spam too).

Part 3 — Build Your First DAG (Step by Step)

Estimated time: 20–25 minutes (we do this together in class)

⏳ Why now? MWAA is still provisioning in the background (Part 2 can take 20–40 minutes). Rather than sit and wait, we'll use that time to build the DAG in Kiro. By the time you finish, the Airflow environment should be up — then you'll access it (Part 4) and upload what you built here.

New to Airflow? Perfect. We'll build one DAG from an empty file, one block at a time, adding each block below in order. By the end you'll have a complete, working pipeline that runs your 3 Glue jobs in sequence.

⏩ Short on time, or just want it to work? Ready-made copies of this DAG are in the backup-dags/ folder of the Live Session bundle:
  • nyc_tlc_pipeline.py — the minimal version
  • nyc_tlc_pipeline_with_alerts.py — the version with SNS alerts
You can upload one of those directly in Part 5 instead of typing. We still recommend building it yourself at least once — that's how the concepts stick.
🧠 What is a DAG? A DAG (Directed Acyclic Graph) is just a recipe that says "run these tasks, in this order." In Airflow you write that recipe in Python. Our recipe: ingest data → clean it → aggregate it.
🧰 Where to write this — create the file in Kiro. Python breaks if the indentation is off, and plain text editors (Notepad, TextEdit) can insert tabs or "smart quotes" that silently break your DAG. Kiro is a real code editor, so it handles indentation correctly.
  1. In Kiro, open the unzipped Live Session folder as your workspace (you already did this to read this guide).
  2. Create a new file named nyc_tlc_pipeline.py in that folder.
  3. Type each block below into the file, in order. Use spaces, not tabs (4 spaces per indent level — Kiro does this automatically when you press Tab).
  4. Save the file. You'll upload it to MWAA in Part 5.

Step 1 — Import the libraries

Every DAG file starts by importing the tools it needs. We need: date helpers, the DAG class itself, and the operator that runs a Glue job.

from datetime import datetime from airflow import DAG from airflow.providers.amazon.aws.operators.glue import GlueJobOperator
  • datetime — to tell the DAG when it's allowed to start running
  • DAG — the container that holds all our tasks
  • GlueJobOperator — a ready-made task that starts an AWS Glue job and waits for it to finish

Step 2 — Define the bare-minimum default_args

default_args are settings applied to every task in the DAG, so you don't repeat yourself. We'll start with the absolute minimum needed to run.

default_args = { 'owner': 'mission-deh-hof', 'retries': 1, }
  • owner — a label showing who owns this DAG (shows up in the UI)
  • retries — if a task fails, try it one more time before giving up
ℹ️ That's genuinely all you need to start. Airflow fills in sensible defaults for everything else. We'll add more later only when we need it.

Step 3 — Define the DAG

Now create the DAG container using a with block. Everything indented under it belongs to this DAG.

with DAG( dag_id='nyc_tlc_pipeline', default_args=default_args, schedule='@monthly', start_date=datetime(2026, 1, 1), ) as dag:
  • dag_id — the unique name you'll see in the Airflow UI
  • schedule='@monthly' — how often it runs (monthly here; use None to only run manually)
  • start_date — the earliest date the DAG is allowed to run

Step 4 — Define the tasks

Each task runs one Glue job. Keep these indented inside the with DAG(...) block. The job_name values must match the Glue jobs the setup script created exactly.

data_ingestion = GlueJobOperator( task_id='data_ingestion', job_name='mission-deh-hof-nyctlc-ingestion', ) raw_to_curated = GlueJobOperator( task_id='raw_to_curated', job_name='mission-deh-hof-raw-to-curated-etl', ) curated_to_aggregated = GlueJobOperator( task_id='curated_to_aggregated', job_name='mission-deh-hof-curated-to-aggregated-etl', )
  • task_id — the task's name in the UI (must be unique within the DAG)
  • job_name — the exact name of the Glue job to run
⚠️ These job names are not optional. They must match what the setup script created: mission-deh-hof-nyctlc-ingestion, mission-deh-hof-raw-to-curated-etl, mission-deh-hof-curated-to-aggregated-etl. A typo here = "job not found" failure.

Step 5 — Set the task dependencies

This one line is the heart of the DAG — it tells Airflow the order. The >> arrow means "then run." Keep it indented inside the DAG block.

data_ingestion >> raw_to_curated >> curated_to_aggregated

Read it left to right: ingest first, then curate, then aggregate. Each task waits for the one before it to succeed.

✅ Checkpoint — Your complete working DAG

Put the 5 blocks together and this is your full file. This alone is a fully working pipeline.

from datetime import datetime from airflow import DAG from airflow.providers.amazon.aws.operators.glue import GlueJobOperator default_args = { 'owner': 'mission-deh-hof', 'retries': 1, } with DAG( dag_id='nyc_tlc_pipeline', default_args=default_args, schedule='@monthly', start_date=datetime(2026, 1, 1), ) as dag: data_ingestion = GlueJobOperator( task_id='data_ingestion', job_name='mission-deh-hof-nyctlc-ingestion', ) raw_to_curated = GlueJobOperator( task_id='raw_to_curated', job_name='mission-deh-hof-raw-to-curated-etl', ) curated_to_aggregated = GlueJobOperator( task_id='curated_to_aggregated', job_name='mission-deh-hof-curated-to-aggregated-etl', ) data_ingestion >> raw_to_curated >> curated_to_aggregated
✅ If you stop here, you have a complete, working DAG. The next part is an optional enhancement — email/SNS alerts — that we'll add once the basic version runs.

Part 3B — Enhancement: Add Success & Failure Alerts (Optional)

Estimated time: 10 minutes

Right now the pipeline runs silently. Let's make it email you via the SNS topic the setup script already created (mission-deh-hof-pipeline-alerts). We'll add two small Python functions and wire them in.

Step 1 — Add two more imports (top of the file)

import boto3 from airflow.operators.python import PythonOperator
  • boto3 — the AWS SDK for Python, used here to publish an SNS message
  • PythonOperator — a task that runs a plain Python function (for our success message)

Step 2 — Add the notification functions (before default_args)

def send_failure_notification(context): """Called automatically when a task fails.""" account_id = boto3.client('sts').get_caller_identity()['Account'] sns = boto3.client('sns', region_name='us-east-1') topic_arn = f"arn:aws:sns:us-east-1:{account_id}:mission-deh-hof-pipeline-alerts" ti = context['task_instance'] sns.publish( TopicArn=topic_arn, Subject='NYC TLC Pipeline FAILED', Message=f"Task '{ti.task_id}' failed in DAG '{ti.dag_id}'.", ) def send_success_notification(**context): """Called when the whole pipeline finishes successfully.""" account_id = boto3.client('sts').get_caller_identity()['Account'] sns = boto3.client('sns', region_name='us-east-1') topic_arn = f"arn:aws:sns:us-east-1:{account_id}:mission-deh-hof-pipeline-alerts" sns.publish( TopicArn=topic_arn, Subject='NYC TLC Pipeline SUCCESS', Message="All 3 stages completed: ingestion, curated, aggregated.", )
ℹ️ Notice the topic name is mission-deh-hof-pipeline-alerts — the exact topic the setup script created. The account ID is looked up automatically, so there's nothing to hardcode.

Step 3 — Hook failure alerts into default_args

Add one line so any task failure triggers the alert:

default_args = { 'owner': 'mission-deh-hof', 'retries': 1, 'on_failure_callback': send_failure_notification, }

Step 4 — Add a success task and extend the dependencies

Inside the DAG block, add a final task that fires the success alert, then put it at the end of the chain:

notify_success = PythonOperator( task_id='notify_success', python_callable=send_success_notification, ) data_ingestion >> raw_to_curated >> curated_to_aggregated >> notify_success
✅ Now a failure in any task emails you automatically, and a clean run ends with a success email. Save the file — you're ready to upload.

Part 5 — Upload Your DAG to MWAA

Estimated time: 3 minutes

MWAA loads DAGs from the dags/ folder of the DAGs S3 bucket. Upload your nyc_tlc_pipeline.py and Airflow picks it up within a minute or two.

Steps

  1. Go to AWS Console → S3 and open the DAGs bucket named mission-deh-hof-airflow-<your-account-id>
  2. Open the dags/ folder inside the bucket
  3. Click Upload → Add files, select the nyc_tlc_pipeline.py you built in Kiro, then click Upload
  4. Open the Airflow UI and refresh — nyc_tlc_pipeline appears in the list within ~1–2 minutes
  5. Flip the DAG's toggle to on (new DAGs arrive paused by default — this unpauses it). If it doesn't start on its own, click Trigger DAG (▶) to run it manually
  6. Open the Graph view to watch each task turn green as it runs
⚠️ If the DAG shows an import error in the UI, click it to read the message. Usual causes: a typo, wrong indentation, or the Amazon provider package missing.
✅ When all tasks are green, your pipeline ran end-to-end — ingestion → curated → aggregated — orchestrated by the DAG you just built. 🎉

Part 6 — Tear It All Down (Do Not Skip)

Estimated time: 15–20 minutes

MWAA bills continuously while it exists. When you finish, run the one-shot teardown. It removes everything the setup created — MWAA first (to stop the hourly billing fastest), then the full pipeline.

Run this

cd ~/scripts && chmod +x mission-deh-hof-teardown-all.sh && ./mission-deh-hof-teardown-all.sh

What happens, in order

PhaseWhat it removes
Step 1 — MWAAEmpties the DAGs bucket (all object versions + delete markers), deletes the CloudFormation stack (MWAA env, VPC, NAT gateways, IAM role), polls until DELETED.
Step 2 — PipelineDeletes Glue jobs/crawlers/databases, Step Functions, EventBridge schedule, SNS topic, DynamoDB tables, the data-lake S3 bucket, and the Glue IAM role.

Wait for the final "ALL DONE — billing has stopped" message.

⚠️ This permanently deletes both S3 buckets and all their contents, the MWAA environment, VPC and networking, DynamoDB tables, and all IAM roles. Download anything you want to keep first.
ℹ️ If the MWAA stack shows DELETE_FAILED, the script prints the failing resources and continues to the pipeline teardown anyway. Re-run the command, or delete the flagged resource in the console, then re-run.
✅ When the stack is gone, billing stops. Confirm in CloudFormation → Stacks that mission-deh-hof-stack no longer appears.
